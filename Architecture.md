# Устройство приложения

Expo SDK 57, React Native 0.86.3, навигация — `expo-router` (типизированные маршруты).
Firebase-проект **общий с сайтом** (`birklik-65289`): те же коллекции, те же правила, те же
облачные функции. Сайт — репозиторий `Birklik.az`, ветка `next-migration`.

Порог входа описан в [README.md](README.md): Expo Go не годится, нужна собственная сборка и
зарегистрированный отладочный токен App Check.

## Три репозитория

```
D:\VS\Birklik.az        сайт
D:\VS\Birklik-mobile    приложение
D:\VS\birklik-core      общая логика — подмодуль `core` у обоих
```

Правка общей логики — **три коммита подряд**: сам пакет, затем указатель в сайте, затем
указатель здесь. Пропустить третий — собраться со старой версией пакета и не понять, почему.

Из пакета приходят типы (`@birklik/core/types`), справочники, тексты на трёх языках и —
важное — **решающие функции**: `isOnDisplay` (что показывать на витрине), `filterProperties`,
`isTierActive`, `tierRemainingDays`, `toImageApiUrl`. Они обязаны быть одни и те же у сайта и
приложения: разойдутся — и один клиент покажет объявление, которое второй скрыл.

## Чем доступ к данным отличается от сайта

Это главное архитектурное различие, и из него растёт почти всё остальное.

```
сайт          читает Firestore на сервере под сервис-аккаунтом — правила его НЕ касаются
приложение    читает клиентским SDK под правилами, как обычный пользователь
```

Поэтому:

- **Правила теперь проверяются по-настоящему.** До приложения почти весь боевой трафик шёл
  мимо них. Любая щель в `firestore.rules` — это щель в приложении.
- **Запрос валидируется по своим условиям, а не по результату.** Выборка без `where`, которая
  по факту вернула бы только свои документы, всё равно отклоняется, если правило требует
  совпадения с `request.auth.uid`. На этом уже спотыкались — см. чистку запросов на отмену.
- **Транзакций на стороне сервера нет.** `createBooking` проверяет пересечение дат запросом, а
  не транзакцией: между проверкой и записью остаётся зазор, и две одновременные брони на те же
  даты обе пройдут. У сайта то же ограничение по другой причине; брони без оплаты, владелец
  разбирает руками.

### Что делается не через SDK, а через сайт

Комментарии и оценки пишутся **не напрямую в Firestore**, а запросом в
`https://birklik.az/api/property/{comments,ratings}` с `Authorization: Bearer <ID-токен>`
(`src/services/interactions-service.ts`). Причина: к этим действиям привязаны пересчёт среднего
рейтинга и уведомление владельцу — логика, которой в правилах не выразить. На сайте она уже
была, и дублировать её в приложении значило бы получить две расходящиеся реализации. Маршруты
проверяют токен, требуют подтверждённой почты и делят одну функцию с серверными действиями
сайта.

## Слои

```
src/app/          экраны, маршрутизация файлами
src/components/   всё остальное визуальное
src/services/     единственное место, где трогают Firestore и Storage
src/auth/         состояние входа
src/i18n/         язык и тексты из пакета
src/filters/      состояние фильтров витрины
src/lib/          Firebase, адреса картинок, разбор кодов ошибок
src/theme/        52 токена, перенесённых из base.css сайта
```

Экраны в `services` не заходят напрямую мимо слоя — это не стиль, а защита от того, чтобы
`isOnDisplay` забыли применить на одном экране из десяти.

### Службы

| Файл | За что отвечает |
|---|---|
| `property-service.ts` | витрина, своё, избранное, похожие, одно объявление |
| `listing-service.ts` | подача и правка, геокодирование, загрузка фотографий |
| `booking-service.ts` | брони: создание, ответ владельца, отмена |
| `favorites-service.ts` | отметка «сохранить» через `arrayUnion`/`arrayRemove` |
| `interactions-service.ts` | комментарии и оценки — через маршруты сайта |
| `moderation-service.ts` | очередь, все объявления, брони, комментарии, жалобы |
| `notifications-service.ts` | чтение и отметка прочитанного |

`toProperty` в `property-service.ts` — **единственная** точка превращения документа в
`Property`. Там же чинятся адреса картинок, и только поэтому их не приходится чинить на
каждом экране.

## Картинки

Две отдельные темы, и их легко спутать.

**Чтение.** В базе часть адресов записана относительным путём `/api/images/...` — сайту
этого довольно, он на том же домене. Приложению нечем достроить: Glide на Android отвергает
адрес без схемы, и выходят серые прямоугольники при исправно работающей сети. Домен
подставляется явно в `src/lib/images.ts`, через прокси сайта — ради кэша Cloudflare и
пережатых размеров, а не прямыми ссылками на Storage.

**Запись.** Совпадает с сайтом до числа, иначе приложение заливало бы фотографии втрое
тяжелее:

```
900 × 675     максимальный размер (вписать, не обрезать; увеличивать нельзя)
0.75          качество
WEBP          один проход кодирования, не два
водяной знак  логотип по центру, 35% ширины (не больше 280), прозрачность 0.20
              высота = ширина × пропорции файла логотипа; оба файла 4:1
              (веб 512×128, приложение 1024×256)
```

**Водяной знак наносится снимком вида, и здесь спрятана ловушка.** Совместить две картинки
вычислением React Native не умеет: `expo-image-manipulator` знает только размер, поворот и
обрезку. Поэтому кадр кладётся в невидимый вид (`watermarked-image.tsx`), а вид снимается
`react-native-view-shot`. Снимается он **в пикселях устройства**: размер вида в точках
умножается на плотность экрана.

Отсюда правило, нарушение которого возвращает мутные фотографии:

```
uploadImages готовит кадр под ПИКСЕЛЬНЫЙ размер вида   ratio × PixelRatio.get()
вид выкладывается по ИТОГОВОМУ размеру в точках        width × height
снимок приводится к итоговому размеру после            resize перед кодированием
```

Пока этой пары не было, снимок 328×675 растягивался до 861×1772 интерполяцией: деталей не
прибавлялось, резкость пропадала, и фотографии из приложения весили 9–18 КБ против 105–213 КБ
у сайта — в **30–100 раз меньше данных на пиксель**. Заодно итоговый размер зависел от
плотности экрана подающего, то есть у разных людей получались разные файлы.

⚠️ Сдвиг логотипа вверх считается от **его собственной высоты** (`-logoHeight / 2`), а не
постоянным числом: на сайте знак стоит ровно в середине, `y = (canvasH - logoH) / 2`.
Постоянные 20 точек совпадали с этим только при ширине логотипа 160.

## Точка на карте

Адрес и точка задаются вместе, как на сайте (`LocationMap` в `listing-editor.tsx`), и связь
работает в обе стороны:

```
кнопка «Найти на карте»  адрес → координаты   geocode()        Nominatim, только AZ
касание карты            координаты → адрес   reverseGeocode() Nominatim /reverse
```

Обратная сторона обязательна: без неё метку переставили бы, а подпись осталась бы от прежнего
места — объявление врало бы о себе.

`LocationPicker` стоит в общей `ListingForm`, поэтому карта есть и при подаче, и при правке
владельцем, и у модератора. Экраны берут `values.coordinates`, а если человек карту не трогал,
работает прежний путь: геокодер по адресу.

⚠️ **Геокодер никогда не отказывает явно** — не найдя места, он возвращает центр Баку. Поэтому
`LocationPicker` сравнивает ответ с `DEFAULT_COORDINATES` и показывает ошибку: молча оставить
метку в столице нельзя, человек решит, что нашлось.

⚠️ Камера двигается **только** по кнопке поиска. Привязать её к текущей точке нельзя — карта
подпрыгивала бы под пальцем на каждом касании.

## Показ объявления

Галерея (`property-gallery.tsx`) повторяет логику сайта: кадр целиком по `contain`, под ним
размытая подложка из того же снимка, счётчик, миниатюры, полный экран. Обрезать нельзя —
владельцы снимают вертикально, и `cover` режет половину комнаты.

## Что может модератор

То же, что на сайте: очередь на проверку, **все** объявления с поиском и фильтрами, правка
любого объявления той же формой, что и владелец, снятие с витрины, удаление, брони,
комментарии, жалобы.

Раздел «все объявления» — не дубль витрины: витрина фильтруется `isOnDisplay`, а модератору
нужны как раз снятые, истёкшие и ожидающие.

Смена тарифа модератором **обязана гасить срок другого тарифа**. Иначе переключение VIP →
Premium оставит `vipExpiresAt` от прошлого, `isTierActive` увидит два действующих тарифа и
объявление получит два значка.

## Оплата

Платные тарифы покупаются **в самом приложении, через Google Play** — уводить на внешнюю
оплату магазины запрещают (правило Apple 3.1.1). Проверено живьём 2026-09-20: покупка
`premium_30` тестовой картой прошла целиком.

```
выбор тарифа      PlanPicker в подаче, кнопка продвижения в «Моих объявлениях»
покупка           expo-iap, товары vip_14 vip_30 premium_14 premium_30
проверка чека     функция verifyPlayPurchase — сервер, не клиент
применение тарифа applyTier: listingTier, isFeatured, срок; объявление уходит к модератору
```

Платное объявление создаётся **черновиком** и выходит из него только после подтверждённой
оплаты — иначе неоплаченный премиум висел бы наверху выдачи. Отказ от оплаты черновик не
удаляет: он виден в «Моих объявлениях» и его можно оплатить потом.

⚠️ Выбор тарифа показывается **только на Android**: в App Store товаров пока нет, и показывать
тарифы без возможности купить незачем.

⚠️ **Тестовой покупку делает не список тестировщиков трека, а отдельное «Лицензионное
тестирование» на уровне аккаунта Play Console.** Пока адреса там нет, Google Play показывает
настоящую карту и настоящую сумму. Признак тестовой покупки — надпись «Тестовая карта» в окне
оплаты и `isTestPurchase: true` в записи `playPurchases`.

## Уведомления

Хранятся на сервере, в `users/{uid}/notifications` — те же самые, что видны в личном кабинете
сайта. Локально на устройстве ничего нет.

Пометка прочитанным и удаление — **разные действия**, путать нельзя: прочитанное остаётся в
списке, удалённое исчезает у обоих клиентов. Так же разделено в вебе.

## Грабли, которые стоили времени

- **Отпечаток подписи в Firebase должен совпадать с тем, чем реально подписан APK.** App Check
  сверяет его **раньше** вердикта Play Integrity, поэтому несовпадение выглядит как что угодно
  другое: токен целостности выдаётся исправно, а Firestore отвечает `PERMISSION_DENIED` и
  объявления не грузятся. Три дня ушли на ожидание проверки выпуска Google, которой не
  требовалось: в Firebase лежал `d76238…`, а Play раздавал сборку, подписанную `9a08fd35…`.
  Проверяется за две минуты и не верится на слово из консоли:
  ```
  adb shell pm path az.birklik.app
  MSYS_NO_PATHCONV=1 adb pull "/data/app/<...>/base.apk" base.apk
  <build-tools>/apksigner.bat verify --print-certs base.apk
  ```
  ⚠️ `keytool -printcert -jarfile` по такому APK молчит — подпись только v2/v3, без JAR-подписи.
  Нужен именно `apksigner`.
- **Пометка `(unreviewed)` у сборки в Play Маркете — не очередь и не помеха.** Внутреннее
  тестирование не рассматривается никогда, это свойство трека. Измерено: со строгим
  `allowUnrecognizedVersion = false` приложение из внутреннего теста работает, то есть
  `PLAY_RECOGNIZED` выдаётся. Распространённое утверждение «метку дают только опубликованным в
  бою» к этому проекту не относится.

- **Metro кэширует карту модулей и пути `tsconfig` при старте.** Новый файл в пакете, новая
  зависимость, новый маршрут — всё это требует перезапуска с `--clear`. Выглядит как «модуль
  не найден» при существующем на диске файле.
- **`user.reload()` меняет объект на месте**, ссылка не меняется, React не перерисовывает.
  Подтверждённая почта не подхватывалась именно поэтому: нужно отдельное состояние.
- **`Pressable` внутри `<Marker>` не получает касаний на Android.** Обработчик вешается на сам
  `Marker`.
- **`LocaleConfig` календаря должен быть выставлен во время отрисовки**, не в эффекте: эффект
  выполняется после первого кадра, и шапка недели остаётся английской.
- **Нативный модуль требует пересборки, чистый JS — нет.** `@expo/vector-icons` и
  `react-native-calendars` подхватываются на ходу; `react-native-svg`, `expo-image-picker`,
  `expo-image-manipulator`, `react-native-view-shot` — нет.
- **Эмулятор на аппаратной отрисовке даёт пустой экран при работающем приложении.** Лечится
  `-gpu swiftshader_indirect`. Снимки экрана при этом возвращают устаревший кадр, а
  `uiautomator dump` показывает правильное содержимое — на этом легко поставить неверный
  диагноз.
