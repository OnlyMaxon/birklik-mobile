# Устройство приложения

Expo SDK 57, React Native 0.86.3, навигация — `expo-router` (типизированные маршруты).
Firebase-проект **общий с сайтом** (`birklik-65289`): те же коллекции, те же правила, те же
облачные функции. Сайт — репозиторий `Birklik.az`, ветка `next-migration`.

Порог входа описан в [README.md](README.md): Expo Go не годится, нужна собственная сборка и
зарегистрированный отладочный токен App Check.

## Три репозитория

```
D:\VS\Birklik.az        сайт
D:\VS\Birklik-mobile    приложение
D:\VS\birklik-core      общая логика — подмодуль `core` у обоих
```

Правка общей логики — **три коммита подряд**: сам пакет, затем указатель в сайте, затем
указатель здесь. Пропустить третий — собраться со старой версией пакета и не понять, почему.

Из пакета приходят типы (`@birklik/core/types`), справочники, тексты на трёх языках и —
важное — **решающие функции**: `isOnDisplay` (что показывать на витрине), `filterProperties`,
`isTierActive`, `tierRemainingDays`, `toImageApiUrl`. Они обязаны быть одни и те же у сайта и
приложения: разойдутся — и один клиент покажет объявление, которое второй скрыл.

## Чем доступ к данным отличается от сайта

Это главное архитектурное различие, и из него растёт почти всё остальное.

```
сайт          читает Firestore на сервере под сервис-аккаунтом — правила его НЕ касаются
приложение    читает клиентским SDK под правилами, как обычный пользователь
```

Поэтому:

- **Правила теперь проверяются по-настоящему.** До приложения почти весь боевой трафик шёл
  мимо них. Любая щель в `firestore.rules` — это щель в приложении.
- **Запрос валидируется по своим условиям, а не по результату.** Выборка без `where`, которая
  по факту вернула бы только свои документы, всё равно отклоняется, если правило требует
  совпадения с `request.auth.uid`. На этом уже спотыкались — см. чистку запросов на отмену.
- **Транзакций на стороне сервера нет.** `createBooking` проверяет пересечение дат запросом, а
  не транзакцией: между проверкой и записью остаётся зазор, и две одновременные брони на те же
  даты обе пройдут. У сайта то же ограничение по другой причине; брони без оплаты, владелец
  разбирает руками.

### Что делается не через SDK, а через сайт

Комментарии и оценки пишутся **не напрямую в Firestore**, а запросом в
`https://birklik.az/api/property/{comments,ratings}` с `Authorization: Bearer <ID-токен>`
(`src/services/interactions-service.ts`). Причина: к этим действиям привязаны пересчёт среднего
рейтинга и уведомление владельцу — логика, которой в правилах не выразить. На сайте она уже
была, и дублировать её в приложении значило бы получить две расходящиеся реализации. Маршруты
проверяют токен, требуют подтверждённой почты и делят одну функцию с серверными действиями
сайта.

## Слои

```
src/app/          экраны, маршрутизация файлами
src/components/   всё остальное визуальное
src/services/     единственное место, где трогают Firestore и Storage
src/auth/         состояние входа
src/i18n/         язык и тексты из пакета
src/filters/      состояние фильтров витрины
src/lib/          Firebase, адреса картинок, разбор кодов ошибок
src/theme/        52 токена, перенесённых из base.css сайта
```

Экраны в `services` не заходят напрямую мимо слоя — это не стиль, а защита от того, чтобы
`isOnDisplay` забыли применить на одном экране из десяти.

### Службы

| Файл | За что отвечает |
|---|---|
| `property-service.ts` | витрина, своё, избранное, похожие, одно объявление |
| `listing-service.ts` | подача и правка, геокодирование, загрузка фотографий |
| `booking-service.ts` | брони: создание, ответ владельца, отмена |
| `favorites-service.ts` | отметка «сохранить» через `arrayUnion`/`arrayRemove` |
| `interactions-service.ts` | комментарии и оценки — через маршруты сайта |
| `moderation-service.ts` | очередь, все объявления, брони, комментарии, жалобы |
| `notifications-service.ts` | чтение и отметка прочитанного |

`toProperty` в `property-service.ts` — **единственная** точка превращения документа в
`Property`. Там же чинятся адреса картинок, и только поэтому их не приходится чинить на
каждом экране.

## Картинки

Две отдельные темы, и их легко спутать.

**Чтение.** В базе часть адресов записана относительным путём `/api/images/...` — сайту
этого довольно, он на том же домене. Приложению нечем достроить: Glide на Android отвергает
адрес без схемы, и выходят серые прямоугольники при исправно работающей сети. Домен
подставляется явно в `src/lib/images.ts`, через прокси сайта — ради кэша Cloudflare и
пережатых размеров, а не прямыми ссылками на Storage.

⚠️ **У подстановки домена есть последствие, и оно кусалось.** `withImageUrls` переписывает
адреса при чтении, а сохранение правки кладёт в документ **показанное** — значит объявление,
правленное с телефона, начинает хранить снимки в виде `https://birklik.az/api/images/...`.
Такого вида разбор не знал: под относительный префикс не подпадает, хост не гугловый, а
`new URL` отрабатывает успешно, поэтому и запасная ветка не срабатывала. Возвращался `null`,
**а удаление молча считало это «нечего удалять»** — снимки правленных объявлений оставались
в хранилище навсегда. Починено в пакете 2026-09-26, разбор знает все четыре вида.

Отсюда правило: **удаление проверяется по хранилищу, а не по исчезновению документа.**
Документ пропадает в обоих случаях, и счётчики сходятся в обоих — они считают разобранное.

**Запись.** Совпадает с сайтом до числа, иначе приложение заливало бы фотографии втрое
тяжелее:

```
900 × 675     максимальный размер (вписать, не обрезать; увеличивать нельзя)
0.75          качество
WEBP          один проход кодирования, не два
водяной знак  логотип по центру, 35% ширины (не больше 280), прозрачность 0.20
              высота = ширина × пропорции файла логотипа; оба файла 4:1
              (веб 512×128, приложение 1024×256)
```

**Водяной знак наносится снимком вида, и здесь спрятана ловушка.** Совместить две картинки
вычислением React Native не умеет: `expo-image-manipulator` знает только размер, поворот и
обрезку. Поэтому кадр кладётся в невидимый вид (`watermarked-image.tsx`), а вид снимается
`react-native-view-shot`. Снимается он **в пикселях устройства**: размер вида в точках
умножается на плотность экрана.

Отсюда правило, нарушение которого возвращает мутные фотографии:

```
uploadImages готовит кадр под ПИКСЕЛЬНЫЙ размер вида   ratio × PixelRatio.get()
вид выкладывается по ИТОГОВОМУ размеру в точках        width × height
снимок приводится к итоговому размеру после            resize перед кодированием
```

Пока этой пары не было, снимок 328×675 растягивался до 861×1772 интерполяцией: деталей не
прибавлялось, резкость пропадала, и фотографии из приложения весили 9–18 КБ против 105–213 КБ
у сайта — в **30–100 раз меньше данных на пиксель**. Заодно итоговый размер зависел от
плотности экрана подающего, то есть у разных людей получались разные файлы.

⚠️ Сдвиг логотипа вверх считается от **его собственной высоты** (`-logoHeight / 2`), а не
постоянным числом: на сайте знак стоит ровно в середине, `y = (canvasH - logoH) / 2`.
Постоянные 20 точек совпадали с этим только при ширине логотипа 160.

## Точка на карте

Адрес и точка задаются вместе, как на сайте (`LocationMap` в `listing-editor.tsx`), и связь
работает в обе стороны:

```
кнопка «Найти на карте»  адрес → координаты   geocode()        Nominatim, только AZ
касание карты            координаты → адрес   reverseGeocode() Nominatim /reverse
```

Обратная сторона обязательна: без неё метку переставили бы, а подпись осталась бы от прежнего
места — объявление врало бы о себе.

`LocationPicker` стоит в общей `ListingForm`, поэтому карта есть и при подаче, и при правке
владельцем, и у модератора. Экраны берут `values.coordinates`, а если человек карту не трогал,
работает прежний путь: геокодер по адресу.

⚠️ **Геокодер никогда не отказывает явно** — не найдя места, он возвращает центр Баку. Поэтому
`LocationPicker` сравнивает ответ с `DEFAULT_COORDINATES` и показывает ошибку: молча оставить
метку в столице нельзя, человек решит, что нашлось.

⚠️ Камера двигается **только** по кнопке поиска. Привязать её к текущей точке нельзя — карта
подпрыгивала бы под пальцем на каждом касании.

### Маршрут от метки на карте объявления

Нажатие на метку открывает окно с названием, местом, ценой и выбором приложения карт — то же
всплывающее окно, что даёт Leaflet на сайте. До этого под картой стояла одна кнопка, и она
сразу открывала системный выбор: куда человек попадёт, до нажатия было неизвестно. Кнопка
осталась и ведёт в то же окно — метка цель мелкая, и не догадавшийся по ней нажать остался бы
без маршрута.

```
Google Maps  https://www.google.com/maps/search/?api=1&query=   как на сайте
Waze         https://waze.com/ul?ll=…&navigate=yes              как на сайте
третья       Apple Maps (iOS) · geo: — системный выбор (Android)
```

Адреса обычные `https`, и это главное: такую ссылку Android отдаёт установленному приложению,
а если его нет — открывает сайт. Своих схем (`comgooglemaps:`) здесь нет намеренно — проверять
их через `canOpenURL` на Android 11 и выше можно только объявив приложение в манифесте, а молча
не открывающаяся кнопка хуже страницы в браузере.

⚠️ **Третья кнопка разная по платформам.** Apple Maps на Android ведёт в никуда, поэтому там на
её месте системный выбор `geo:` — ровно то, что делала прежняя кнопка. Через него открываются и
Yandex Maps, и 2GIS, которыми в Азербайджане пользуются не меньше.

⚠️ **Окно закрывается только крестиком.** Закрывать его касанием карты было бы привычнее, но
нажатие по метке на Android доходит и до карты: окно открылось бы и тут же закрылось.

## Показ объявления

Галерея (`property-gallery.tsx`) повторяет логику сайта: кадр целиком по `contain`, под ним
размытая подложка из того же снимка, счётчик, миниатюры, полный экран. Обрезать нельзя —

## Ссылки birklik.az открывают приложение

Собрано из двух половин, и работает только когда обе на месте:

```
сайт        https://birklik.az/.well-known/assetlinks.json   статикой в public/
приложение  intent-filter с autoVerify в AndroidManifest     + +native-intent.tsx
```

Файл на сайте — согласие сайта, фильтр в манифесте — согласие приложения. Android при
установке сам идёт за файлом и сверяет отпечаток подписи. Не сошлось — фильтр молча не
работает, ссылка уходит в браузер; ни ошибки, ни окна выбора человек не увидит.

**Просим только объявления**, а не весь домен:

```
/property/<id>      /az/property/<id>      /ru/property/<id>      /en/property/<id>
```

Кабинет, документы и посадочные страницы городов приложение не повторяет, и перехватывать их
значило бы уводить человека в пустоту. Кнопка «Поделиться» на странице объявления даёт ровно
такой адрес — то есть делятся именно тем, что приложение открыть умеет.

⚠️ **Адреса сайта и маршруты приложения не совпадают**, поэтому путь переводится в
`app/+native-intent.tsx`. У азербайджанской версии сайта префикса нет, у русской и английской
есть, а в приложении язык живёт в настройках, а не в адресе:

```
birklik.az/property/abc      → /property/abc    совпало само
birklik.az/ru/property/abc   → /property/abc    префикс снят
birklik.az/ru/kiraye/baku    → /                 экрана нет, домой
birklik://…  ·  запуск с рабочего стола  → БЕЗ ИЗМЕНЕНИЙ
```

⚠️ `redirectSystemPath` получает **полный адрес со схемой**, а не путь, и получает его на
каждый запуск приложения — не только на переход по ссылке. Поэтому всё, что не `http(s)` с
нашего домена, возвращается как есть: тронув это, сломаешь обычный запуск с рабочего стола.

⚠️ Ключа загрузки среди отпечатков в `assetlinks.json` нет — там три, выданных Play Console.
Проверять ссылки можно только на сборке, поставленной **из магазина**: у собранного здесь apk
подпись другая, и Android откажет.

## Что может модератор

То же, что на сайте: очередь на проверку, **все** объявления с поиском и фильтрами, правка
любого объявления той же формой, что и владелец, снятие с витрины, удаление, брони,
комментарии, жалобы.

Раздел «все объявления» — не дубль витрины: витрина фильтруется `isOnDisplay`, а модератору
нужны как раз снятые, истёкшие и ожидающие.

Смена тарифа модератором **обязана гасить срок другого тарифа**. Иначе переключение VIP →
Premium оставит `vipExpiresAt` от прошлого, `isTierActive` увидит два действующих тарифа и
объявление получит два значка.

**Чужие снимки модератор удаляет с 2026-09-26.** Правила хранилища пускают к удалению
владельца папки **или** обладателя метки `moderator` в токене — той же, что уже используют
правила Firestore. Серверная функция для этого не нужна: правила хранилища читают тот же
токен, а вот до Firestore они дотянуться не могут, поэтому метка — единственный рабочий
источник истины.

⚠️ До этого удаление чужого снимка работало **наполовину и молча**: адрес уходил из
документа, фотография пропадала, а файл оставался в хранилище и был открыт на чтение по
прямой ссылке (`allow read: if true`). Отказ проглатывался пустым `catch`. Теперь отказы
считаются и уходят в журнал с причиной.

### Блокировка человека

Раздел «Люди» и кнопка «Заблокировать» в окне человека. Появились из требования Apple к
приложениям с чужим контентом (правило 1.2): жалоба, контакты и **возможность заблокировать
нарушителя**. Первые две были, третьей не было.

⚠️ **Раньше раздела «Люди» здесь не было намеренно**, и причина записана была такая: список из
ста сорока учётных записей на телефоне бесполезен, а действий над ними всё равно нет. Второе
перестало быть правдой. Первое осталось, поэтому список открывается **поиском**: без запроса
показываются только заблокированные — ровно те, к кому модератор возвращается.

Что запрещает блокировка: объявления, комментарии, оценки, брони. Вход и просмотр остаются —
человек должен прочитать причину и дотянуться до поддержки.

⚠️ **Единственное действие модераторки, которое идёт НЕ записью в Firestore.** Всё остальное
здесь пишется прямо из приложения, потому что правила дают модератору полный доступ по заявке
в токене. Блокировка так не умеет: она ставит заявку `blocked` другому человеку, отзывает его
токены и снимает его объявления — это только Admin SDK. Поэтому `setUserBlocked` на сервере,
и её же зовёт сайт.

Причину человек видит полосой `BlockedNotice` — профиль, свои объявления, подача объявления.
Узнать о запрете надо до того, как заполнишь анкету и получишь отказ при сохранении.

⚠️ Признак проводится в `Profile` **явным полем**: провайдер собирает профиль по полям, и всё
неперечисленное теряется. Забудешь — полоса не покажется никогда, а блокировка будет выглядеть
поломкой приложения.

⚠️ Отказ в комментарии и оценке приходит кодом `blocked` от сервера сайта и переводится в текст
`errors.blocked`. Запрет живёт там, а не здесь: комментарии пишет сервис-аккаунт, которого
правила не касаются. Подробности — в `Architecture.md` веб-репозитория.

## Оплата

Платные тарифы покупаются **в самом приложении, через Google Play** — уводить на внешнюю
оплату магазины запрещают (правило Apple 3.1.1). Проверено живьём 2026-09-20: покупка
`premium_30` тестовой картой прошла целиком.

```
выбор тарифа      PlanPicker в подаче, кнопка продвижения в «Моих объявлениях»
покупка           expo-iap, товары vip_14 vip_30 premium_14 premium_30
подъём            СВОЙ экран account/boost/[id], товары boost_1 … boost_10 — см. ниже
проверка чека     функция verifyPlayPurchase — сервер, не клиент
применение тарифа applyTier: listingTier, isFeatured, срок; объявление уходит к модератору
```

Платное объявление создаётся **черновиком** и выходит из него только после подтверждённой
оплаты — иначе неоплаченный премиум висел бы наверху выдачи. Отказ от оплаты черновик не
удаляет: он виден в «Моих объявлениях» и его можно оплатить потом.

⚠️ Выбор тарифа показывается **только на Android**: в App Store товаров пока нет, и показывать
тарифы без возможности купить незачем.

⚠️ **Тестовой покупку делает не список тестировщиков трека, а отдельное «Лицензионное
тестирование» на уровне аккаунта Play Console.** Пока адреса там нет, Google Play показывает
настоящую карту и настоящую сумму. Признак тестовой покупки — надпись «Тестовая карта» в окне
оплаты и `isTestPurchase: true` в записи `playPurchases`.

### Две кассы: Google Play и App Store

С 2026-10-21 оплата работает на обеих платформах. Прежде стояло «только Android» в четырёх
местах — слушатели покупок, список тарифов при подаче, кнопки на странице объявления и вход из
«Моих объявлений», — и снимать их надо было **вместе**: оставь одно, и на iPhone кнопка есть, а
покупка молча не начинается.

```
проверка чека   Android → verifyPlayPurchase, iOS → verifyApplePurchase
товары          имена ОДНИ И ТЕ ЖЕ в Play Console и App Store Connect
поле чека       purchaseToken у обоих: у Apple в нём подписанная квитанция (JWS)
```

Функции на сервере две, а не одна: у Google доказательство — токен, о котором сервер спрашивает
Google; у Apple — подпись самой квитанции, которую сервер проверяет у себя. Одна функция на обе
кассы означала бы внутри неё догадку «а чей это чек», решающую судьбу денег.

⚠️ **У Apple НЕТ аналога `obfuscatedProfileId`** — поля, которым 2026-10-10 закрыли дыру «убили
процесс после оплаты → приложение забыло номер объявления → деньги списаны, тариф не поставлен».
Apple принимает только `appAccountToken`, и он **обязан быть UUID**. Поэтому перед открытием
окна оплаты приложение пишет `purchaseIntents/{uuid}` с номером объявления, а в покупку кладёт
ключ. Запись делается ДО оплаты: после неё может уже не быть ни экрана, ни процесса.

⚠️ **Не-UUID StoreKit выбрасывает МОЛЧА.** Квитанция приедет без привязки, дыра откроется снова,
и ошибки не будет нигде. UUID собирается из `Math.random` намеренно: нативного источника
случайности в приложении нет, а стойкость тут не нужна — это ключ к записи, не пароль. Чтобы
чужой UUID попал в квитанцию, надо заплатить своими деньгами, а сервер сверяет владельца.

⚠️ **`onlyIncludeActiveItemsIOS: false` задано явно**, и на нём держится вся защита от обрыва на
iOS. «Действующими» StoreKit считает то, чем человек продолжает владеть: непотребляемые товары и
живые подписки. Наши тарифы и подъёмы — расходуемые, и в тот список не попадают. Умолчание
означало бы, что прерванная покупка здесь просто не появится.

### Какую ступень предлагаем

Решает тариф, который **действует**, а не поле `listingTier`: у истёкшего платного оно
остаётся прежним.

```
обычное или истёкшее   обе ступени: VIP и Premium
действует VIP          продлить VIP либо перейти на Premium
действует Premium      только продлить Premium
```

⚠️ **Premium-у VIP не предлагается — это защита, а не упущение.** Оплата VIP идёт через
`applyPaidTier`, а она стирает дату прежнего тарифа: объявление стало бы VIP, а оплаченные дни
Premium сгорели бы. Вместо кнопки стоит строка, объясняющая, почему её нет.

Сайт выровнен по этой схеме 2026-10-10 (раньше VIP-объявлению он предлагал только Premium, а
Premium-объявлению — ни одной кнопки).

### Подъём: наверх своей полосы

Подъём (`İrəli çək`) поднимает объявление наверх **своей** полосы и за её пределы не выводит:
поднятое обычное обгоняет все обычные и остаётся ниже любого VIP и Premium. Правило целиком
живёт в общем пакете, `core/src/utils/boost-helper.ts`, и считает его `compareListings` —
единственная сортировка выдачи на площадке.

```
товары       boost_1 boost_3 boost_5 boost_10  (BOOST_PRODUCTS, расходуемые)
цена         2 / 5 / 8 / 15 манатов            (BOOST_PRICES в общем пакете)
экран        account/boost/[id] — только он; вход один, кнопка на странице объявления
применение   applyBoostPackage: boostedAt сейчас же + остаток в boosts/{id}
расход       ночная dailyBoosts, по одному подъёму в сутки, запись удаляется на последнем
```

⚠️ **У подъёма свой экран, и из продвижения он убран совсем** (решение владельца 2026-10-14).
До этого пакеты лежали блоком внизу `account/promote/[id]`, а кнопка вела туда с параметром
`focus`. Причина переноса не в красоте: продвижение продаёт ступень на срок, подъём — сутки в
своей полосе, и человек, пришедший за вторым, читал условия первого. Экран объясняет услугу
схемой полос (куда именно встанет объявление) и тремя шагами, а не одной строкой.

⚠️ **Итог подъёма на экране продвижения всё равно остался — убирать его нельзя.** Незавершённые
покупки забираются при открытии ЛЮБОГО экрана с оплатой: человек мог купить подъём, закрыть
приложение до проверки чека и вернуться в продвижение. Показать там «тариф до 1970-01-01»
значило бы соврать.

⚠️ **Экран подъёма отказывает ДВАЖДЫ, и второй отказ — про деньги.** Действующий VIP или
Premium — нечего продавать. Объявление не на витрине (`status !== 'active'`) — сутки подъёма
истекли бы раньше, чем его кто-то увидит. Второе повторяет серверную проверку в
`initiatePayment`, но **только для карты**: оплата через Google Play таких проверок не делает
вовсе — она применяет оплаченное, потому что деньги уже списаны. Значит отказать обязан экран.

Первый подъём делается в момент оплаты — человек заплатил и должен увидеть результат сразу, —
поэтому пакет на один подъём записи не создаёт вовсе. Повторная покупка **прибавляется** к
остатку: в отличие от `applyPaidTier`, подъём оплаченного не сжигает.

⚠️ Витрине приложения отдельная выборка поднятых НЕ нужна, в отличие от сайта: здесь все
объявления приходят разом (`getAllForFilter`, предел 300), и порядок целиком решает сортировка.
Сайту нужны ещё два запроса, потому что его лента режется курсором по дате — и старое поднятое
объявление лежало бы на третьей странице.

⚠️ **Подъём предлагается только обычному объявлению.** Код поддерживает любую полосу, но у VIP
и Premium кнопка скрыта, а сервер отказывает такому платежу **до** списания денег: эти два и
так стоят выше всех обычных.

⚠️ **`VerifyResult` теперь разбирается по полю `kind`, и это не формальность.** Незавершённая
покупка забирается при открытии ЛЮБОГО экрана — значит экран подачи объявления может получить
ответ про подъём. Без разбора он показал бы «тариф действует до» с пустой датой.

### Что человек видит до и после оплаты

Перечни возможностей и пределы на число снимков живут в общем пакете: `TIER_PHOTO_LIMITS`,
`photoLimitForTier`, `pricing.features` в словарях. Раньше они были литералами внутри
редактора на сайте — отсюда и 15 снимков всем тарифам в приложении, молча отрезавшиеся при
загрузке, при обещанных сайтом 20 и 30.

После оплаты показывается не дата, а **что человек получил**: ступень, срок и её перечень
возможностей. Какая ступень — спрашивается у перечитанного объявления, а не у нажатой кнопки:
после подхваченной незавершённой покупки нажатия не было вовсе.

### Полоса загрузки и окно итога вместо системных

Подача объявления — самое долгое действие в приложении: двадцать снимков с водяным знаком на
небыстром телефоне это десятки секунд. Системный кружок всё это время не отличим от зависшего
приложения, и человек жмёт «назад», теряя полчаса работы.

```
SubmitProgress   полоса с ДОЛЕЙ и подписью шага; доля настоящая, по сделанному
StatusDialog     окно итога: рисунок, объяснение, кнопка, связь с поддержкой
где              account/add.tsx и account/edit/[id].tsx — форма у них одна
```

⚠️ **Доля считается по настоящим шагам, а не по таймеру.** `uploadImages` зовёт `onProgress`
после каждого снимка, и полоса показывает «фото 7 из 20». Бегунок «ради вида» хуже кружка: он
обещает срок, которого никто не обещал.

⚠️ Доли шагов неровные намеренно (`STEP` в `account/add.tsx`): снимки занимают большую часть
времени и получают от десятой до трёх четвертей полосы. Место на карте и запись документа —
края.

⚠️ **Окно итога умеет то, чего не умеет `Alert.alert`:** рисунок, объяснение в две фразы,
приписку и **связь с поддержкой** — звонок и почта из общих текстов `pages.contact`, тех же,
что на странице контактов сайта. Своей копии номера здесь нет: номер меняется, и забытая копия
отправляет человека в никуда.

⚠️ Окно успеха после подачи **не закрывается ни подложкой, ни кнопкой «назад»** — только
кнопкой «К моим объявлениям». Форма под ним заполнена, и вторая отправка создала бы второе
объявление. У окна ошибки наоборот: закрыть можно, а кнопка «Попробовать снова» повторяет
отправку одним нажатием. Повтор безопасен — `createListing` последнее ожидание в кладке, и до
него дело не дошло.

## Сборка для iOS — через EAS

iOS собирается в облаке Expo: `eas build -p ios --profile production`, затем
`eas submit -p ios --latest`. Mac не нужен — сборка идёт на их машинах, сертификаты и профили
EAS создаёт сам по ключу App Store Connect API.

⚠️⚠️ **EAS только для iOS. Никогда `-p android` и никогда `-p all`.** Папки `android/` в гите
нет, и значки, заставка и `versionCode` живут **в ней руками**. Облачная сборка начинается с
`expo prebuild`, то есть собрала бы `android/` заново из `app.json` — и всё это потеряла бы
молча. Android как собирали, так и собираем: локально, своим ключом.

⚠️ **В `eas.json` нельзя написать комментарий** — поэтому предупреждение выше живёт здесь, а не
рядом с кодом. Это единственная причина; будь там комментарии, оно стояло бы первой строкой.

⚠️ `appVersionSource: "local"` и `autoIncrement: false` заданы нарочно: версию и номер сборки
мы ведём РУКАМИ, как и у Android. Дай EAS считать их самому — и номер в `app.json` разойдётся с
тем, что ушло в магазин, причём узнаем мы об этом из Play Console или App Store Connect.

### Файлы, которых у EAS нет

`.env`, `google-services.json` и `GoogleService-Info.plist` в гите отсутствуют, а EAS загружает
только закоммиченное. Их надо отдать отдельно — файловыми переменными окружения.

⚠️ **Тут есть нерешённый вопрос, и решать его придётся до первой сборки.** Статический
`app.json` переменных окружения читать не умеет, поэтому `ios.googleServicesFile` в нём пока
НЕ задан: указать путь к файлу, которого в сборке не будет, значило бы получить падение сборки
или — хуже — приложение без доступа к Firebase. Выход один из двух: перейти на `app.config.js`
(тогда путь берётся из переменной) либо держать файл в сборочном контексте иначе. Выбор не
сделан.

### Значок iOS — отдельным файлом

`ios.icon` указывает на `assets/images/icon-ios.png`, а не на общий `icon.png`.

⚠️ **Apple не принимает значок с прозрачностью**, и отказ приходит от самой заливки, до
проверки человеком. Общий `icon.png` — 1024×1024 **RGBA**. Expo, возможно, сплющивает альфу
сам, но живьём мы этого не видели, а проверять предположением уже обжигались. Файл делается
`node store/icon-ios.js` (`flatten` подкладывает белый фон и убирает альфу; `removeAlpha`
нельзя — полупрозрачные края стали бы чёрными).

Имя с пометкой платформы намеренно: второй `icon.png` рядом с первым через полгода никто не
отличит, а разница между ними — причина отказа магазина.

### Строки разрешений — на трёх языках

У приложения одно разрешение: фото-библиотека (камера и местоположение не используются вовсе,
это проверено по коду). Строка задана через `expo.locales` — `assets/locales/{az,ru,en}.json`, —
а не только в `infoPlist`.

⚠️ Одной строки в `infoPlist` хватило бы, чтобы пройти проверку, но человек увидел бы запрос на
чужом языке. `locales` — первоклассная возможность Expo: из этих файлов собираются
`InfoPlist.strings` по языкам. Значение в `infoPlist` остаётся запасным — для языков, которых в
списке нет.

### Ссылки birklik.az на iPhone

`ios.associatedDomains: ["applinks:birklik.az"]` — это ПЕРВАЯ половина.

⚠️ Вторая половина на сайте: файл `apple-app-site-association` рядом с `assetlinks.json`, и в
нём нужен **Team ID**. Без него ссылка молча откроется в браузере — точно та же история, что со
сборкой 15 на Android, где половины тоже две.

## Уведомления

Хранятся на сервере, в `users/{uid}/notifications` — те же самые, что видны в личном кабинете
сайта. Локально на устройстве ничего нет.

Пометка прочитанным и удаление — **разные действия**, путать нельзя: прочитанное остаётся в

## Грабли, которые стоили времени

- **Отпечаток подписи в Firebase должен совпадать с тем, чем реально подписан APK.** App Check
  сверяет его **раньше** вердикта Play Integrity, поэтому несовпадение выглядит как что угодно
  другое: токен целостности выдаётся исправно, а Firestore отвечает `PERMISSION_DENIED` и
  объявления не грузятся. Три дня ушли на ожидание проверки выпуска Google, которой не
  требовалось: в Firebase лежал `d76238…`, а Play раздавал сборку, подписанную `9a08fd35…`.
  Проверяется за две минуты и не верится на слово из консоли:
  ```
  adb shell pm path az.birklik.app
  MSYS_NO_PATHCONV=1 adb pull "/data/app/<...>/base.apk" base.apk
  <build-tools>/apksigner.bat verify --print-certs base.apk
  ```
  ⚠️ `keytool -printcert -jarfile` по такому APK молчит — подпись только v2/v3, без JAR-подписи.
  Нужен именно `apksigner`.
- **Пометка `(unreviewed)` у сборки в Play Маркете — не очередь и не помеха.** Внутреннее
  тестирование не рассматривается никогда, это свойство трека. Измерено: со строгим
  `allowUnrecognizedVersion = false` приложение из внутреннего теста работает, то есть
  `PLAY_RECOGNIZED` выдаётся. Распространённое утверждение «метку дают только опубликованным в
  бою» к этому проекту не относится.

- **Metro кэширует карту модулей и пути `tsconfig` при старте.** Новый файл в пакете, новая
  зависимость, новый маршрут — всё это требует перезапуска с `--clear`. Выглядит как «модуль
  не найден» при существующем на диске файле.
- **`user.reload()` меняет объект на месте**, ссылка не меняется, React не перерисовывает.
  Подтверждённая почта не подхватывалась именно поэтому: нужно отдельное состояние.
- **`Pressable` внутри `<Marker>` не получает касаний на Android.** Обработчик вешается на сам
  `Marker`.
- **`<Link asChild>` молча теряет стиль, записанный функцией.** `expo-router` отдаёт ребёнка
  компоненту `Slot` из Radix, а тот сливает свойства как `style = {...свои, ...детские}`.
  Привычная для `Pressable` запись `style={({pressed}) => [...]}` — функция, а разворот функции
  в объект даёт пусто: своих перечислимых свойств у функции нет. Элемент остаётся **без единого
  стиля**, и ни ошибки, ни предупреждения не будет — массив `expo-router` проверкой в разработке
  ловит, функцию не ловит никто. На этом компактная сетка вышла в магазин рваной: карточке не
  доезжал `flex: 1`, ширину задавало содержимое, и столбцы получались разной ширины. В обычном
  виде карточка и так во всю ширину, поэтому пропажа подложки и теней сходила за «плоский» вид
  и в глаза не бросалась. Поэтому ссылка-карточка живёт в одном месте — `components/card-link.tsx`,
  где `Pressable` получает ОДИН плоский объект, а нажатие отслеживается своим состоянием.
- **`LocaleConfig` календаря должен быть выставлен во время отрисовки**, не в эффекте: эффект
  выполняется после первого кадра, и шапка недели остаётся английской.
- **Нативный модуль требует пересборки, чистый JS — нет.** `@expo/vector-icons` и
  `react-native-calendars` подхватываются на ходу; `react-native-svg`, `expo-image-picker`,
  `expo-image-manipulator`, `react-native-view-shot` — нет.
- **Эмулятор на аппаратной отрисовке даёт пустой экран при работающем приложении.** Лечится
  `-gpu swiftshader_indirect`. Снимки экрана при этом возвращают устаревший кадр, а
  `uiautomator dump` показывает правильное содержимое — на этом легко поставить неверный
  диагноз.
